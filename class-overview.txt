This document seeks to explain a reasonable "first cut" architecture of the project, from which we can iterate and improve. See the attached class diagram for more info on the relationships between the classes.

For the first cut, I suggest we start with a command line interface, and store all the data in a JSON file. I think the class diagram, and below details, are a good starting point from which we can add additional features.

Perhaps a first cut at organization could be:

	model/
		Event
		Reservation

	repository/
		EventRepository
		JsonEventRepository

	service/
		EventService
		EventQuery
		EventStatistics
		ValidationException

	ui/
		EventListUI
		EventEditorUI
		ReservationListUI
		ReservationEditorUI

	ui/cli/
		EventListCLI
		EventEditorCLI
		ReservationListCLI
		ReservationEditorCLI

	config/
		ApplicationConfig

	app/
		EventRegistrationApplication

The data persistence layer is abstracted out. In terms of modifying data through a UI, the EventListUI delegates changes to other UI's (a nested pattern), and then modifies the correspoding Event object via the EventService.

For example, if you wanted to create a new Event:

	- EventListUI: opens EventUI, and awaits a return value.
		- The EventUI will allow the user to set values of a temporary Event
			- The EventUI itself can allow for reservations to be modified, via ReservationListUI. Eg, if the user wants to add / edit reservations, they will enter the ReservationListUI
				- The ReservationListUI will populate the List<Reservation> object of the event.
			- Upon ReservationListUI returning, the EventUI will receive an Event that has reservations populated.
		- Eventually, the EventUI returns the Event (with the fields and reservations set) to the EventList UI, which will then tell EventService to store it.

I did not go into specific details of validations for each use case, yet, but it should be easy to implement those validations. (Eg, you cannot "add" a reservation if capacity is null or # reservations is too many already)
		
Now.. onto the classes


DATA MODEL / ACCESS CLASSES
		
	- Event: Object that represents an event
		- id (int)
		- title (string)
		- description (string)
		- venue_name (string)
		- venue_address (string)
		- venue_details (string)
		- datetime start (datetime)
		- datetime end (datetime)
		- capacity
		- reservations (list of Reservation objects)
		
	- Reservation: Object that represents a person attending an event
		- first name (string)
		- last name (string)
		- email (string)
		- phone (string)
		- date_registered (datetime)
		
		* note: for simplicity, this is a composition.. the reservations live within an event object, and therefore do not have their own IDs.
		
	- EventService:
		Purpose:
			- basically wraps a concrete EventRepository instance
			- provides a level of abstraction from how application data is actually stored.
			- ability to return queried-for events (eg: filtered, sorted)
			- a place to contain logic of validation
				- we may want to organize this better or abstract this out later, validation logic increases in complexity
		
		Implementation:
			- likely will eventually be passed a Config object, so that it can instantiate the correct Repository type
				- file might specify what type of datastore to use, and whatever params
					- eg: cloud (credentials, urls), flatfile (filepath), etc
			- for now, we will just have it instantiate a JsonEventRepository.
			- the EventQuery object represents the filter/sort objectives, as an object.
				- (we can rename this to "View" possibly)
			
	- EventRepository / JsonEventRepository:
		Purpose:
			- this class manages actual data persistence.
			- for now, we expect basic operations:
				- loadAll
				- saveAll
				- insertEvent
				- updateEvent
				- deleteEvent
		
		Implementation:
			- let's start with one example concrete implementation: JsonEventRepository
			- should be able to read a Json file, and parse it into Event objects (with reservations: List<Reservation>)
			- should be able to save a list of Events
			- we allow insert/update/save, so that if we ever move to a DB this is natural fit
		
		
UI CLASSES
		
	- EventListUI (eg: EventListCLI)
		Purpose: Allows the user to:
			- view all/some events
				- allows filter/sort
			- manage events
				- add, view, edit, delete
			
		Interaction:
			- ability to choose a field to filter by, and provide a string to filter.
				- we can add more functionality to filters in the future
					- eg: multiple filters at once, date filter, "isNotFull", "isNotEmpty"
				- first cut: Title, description, venue -- case insensitive search
			- ability to sort the list of filtered events
				- choose a column, and asc/desc
			- ability to tell UI to add an event
			- ability to tell UI to view/edit/delete a particular event
			
		Implementation details:
			Event Management:
				- add event
					- opens a new EventGUI, which (upon success) will optionally return an Event object
						- if Event object is returned: insert it via EventService, and refresh.
						- if no Event object is returned: user aborted, just refresh.
				- delete an event:
					- allows "deletion" of event, whereby it is removed via EventService
				- view / edit:
					- opens a new EventGUI, which will be passed a *copy* of the Event.
					- if Event object is returned: it has been modified, update it via EventService, and refresh.
					- if Event null is returned: nothing to do, just refresh.
			Display:
				- can add a filter, or set a field to sort by (with direction: asc or desc)
				
		If GUI:
			- show a list view of all events.
				- clicking a header alters sort.
				- clicking a row "selects" that event, enabling the "view/edit/delete" buttons
			- have a textbox, and a dropdown with selectable columns (title, description, venue)
			- have a fitler button. when pressed, will filter by the above configuration
			- have a button to "add event"
		
		If CLI:
			- print out a table of events, with their IDs
			- allow user to enter commands:
				- "add":  enters the EventUI
				- "edit <id>" or "view <id>": enters the EventUI for the event whose ID is <id>
				- "delete <id>": after confirmation, deletes event whose ID is <id>
				- for filtering:
					- "filterby title <string>": shows all events whose title contains <string>
					- "sortby 3 desc": sorts by the 3rd column, descending
				
		
	- EventUI
		Purpose: Allows the user to:
			- edit an existing event, or create a new one.
			- jump into the "manage reservation" UI
			
		Interaction:
			- ability to modify particular Event field values
			- ability to view metadetails (eg, how many reservations, how much capicity left, time until event starts, etc)
			- enter a UI to manage the reservations of the Event
			
		Implementation details:
			- edit event fields
				- user can modify the event title, description, etc.
			- user can eventually do either:
				- save:  returns the Event to the caller (meaning that there have been accepted changes)
				- abort: returns null to the caller (meaning that no changes were made)
			- user can enter the "manage reservations" UI for the event. this will pass it a deep copy, so that changes made in the ReservationListUI are not permenant until the EventUI decides to adopt them after control is returned to it.
				
		If GUI:
			- show a form with text inputs for applicable fields
			- show whatever additional metadata is useful
			- show a button for "save" and "abort"
			- show a button for "manage reservations"
		
		If CLI:
			- show fields and values
			- show whatever additional metadata is useful
			- allow user to enter commands:
				- "set <field> <value>": changes the Event's <field> value to be that of <value>.
					- eg: "set title new title" would set title to "new title"
				- "reservations": enters the ReservationListUI for this Event
				- "save" or "abort"
			
	- ReservationListUI
		Purpose: Allows the user to:
			- view all reservations (and whatever computed data we want)
			- add / edit / delete reservations
			
		Interaction:
			- ability to edit a particular reservation
			- ability to add a reservation
			- ability to delete a particular reservation
			
		Implementation details:
			- for now, this can display a table of all reservation
			- the user can then interact to do whatever above actions they desire
			- on add: open the ReservationUI, and wait for return.
				- if Reservation object: add it to the event.reservations list.
				- if no Reservation object: do nothing, user aborted adding.
			- on delete:
				- confirm user wants to delete. if they confirm, remove it from event.reservations List.
			- on edit: opent he ReservationUI, passing it a *copy* of the reservation. wait for return.
				- if Reservation object: replace the matchin reservation in event.reservations.
				- if no Reservation object: do nothing, user aborted editing.
				
		If GUI:
			- show list table of all the reservations (name, number, date registered, etc)
			- allow user to click "add reservation" to enter ReservationUI
			- allow user to click a row to select a reservation
				- would enable clicking "edit reservation" or "delete reservation"
		
		If CLI:
			- print table of all reservations, include an "id" for each (eg: row number)
			- show whatever additional metadata is useful
			- allow user to enter commands:
				- "add": enters the ReservationUI
				- "edit <id>": enters the ReservationUI passing it the corresponding Reservation object
				- "delete <id>": removes the corresponding Reservation object from the event.reservations List
	
	- ReservationUI
		Purpose: Allows the user to:
			- edit an existing Reservation, or create a new one
			
		Interaction:
			- ability to modify particular Reservation field values
			
		Implementation details:
			- edit Reservation fields
				- user can modify the name, phone, etc
			- user can eventually do either:
				- save:  returns the Reservation to the caller (meaning that there have been accepted changes)
				- abort: returns null to the caller (meaning that no changes were made)
				
		If GUI:
			- show a form with text inputs for applicable fields
			- show whatever additional metadata is useful (eg, event details)
			- show a button for "save" and "abort"
		
		If CLI:
			- show fields and values
			- show whatever additional metadata is useful
			- allow user to enter commands:
				- "set <field> <value>": changes the Reservation's <field> value to be that of <value>.
					- eg: "set email foo@bar.com" would set the email field to "foo@bar.com"
				- "save" or "abort"
